## Architecture rules
- Editor engine lives in `src/lib/editor/` (pure types/render/mix/export); UI in `src/components/editor/`. Why: one `renderFrame` is shared by preview and export so they always match.
- Timeline is stored as JSON in `projects.timeline`; captions live in `caption_tracks` rows. Why: captions are edited/translated independently and saved per track.
- Media files go to the private `media` bucket under `<userId>/...`; playback uses signed URLs, decoding (export, transcription) always uses the signed remote URL. Why: blob URLs don't support range requests needed by mediabunny.
- Export runs fully in the browser via mediabunny (WebCodecs), preferring H.264/AAC with VP9/AV1 + Opus MP4 fallbacks. Why: no server video processing on Workers.
- Transcription: client mixes timeline audio at 16 kHz, splits on silence, sends short WAV chunks to `/api/transcribe` (bearer-verified). Why: the gateway endpoint returns no timestamps, so chunk boundaries provide cue timing.
- tsconfig is strict (noUncheckedIndexedAccess, exactOptionalPropertyTypes); optional fields are typed `?: T | undefined`.
- Rendering is a layered compositor: each visual clip renders into its own full-frame layer (`renderClipLayer`), then effects run on the layer and transitions composite layers. Why: transitions need both clips, and per-clip effects must not touch other tracks.
- Color filters/adjustments use pixel color matrices (`fx.ts`), not `ctx.filter` (only blur uses it, with a fallback). Why: `ctx.filter` is ignored in some browsers, which made effects silently disappear.
- The pointwise color stage (matrix → filter grade → tonal detail) runs in a single `getImageData`/`putImageData` round trip per layer. Why: three read-backs per clip per frame is what made adding a filter or an adjustment hitch.
- A clip's `transitionIn` blends from the touching previous clip on the same track; that clip stays rendered past its end for the transition length (`outgoingTail`), in preview and export. Why: joint-centred transitions between clips without overlapping them.
- A transition is its own timeline object drawn inline on the clip lane (the same row as the videos, like the marketing mock), not a separate band or a badge on top of a clip. Its block is described by `duration` plus a display-only `bias` (the lane's centre offset from the cut); `transitionBlockSpan` returns `center = c.start + bias` so the chip straddles wherever the user left it, and `ClipBlock` still keeps the clip's full rectangle - editing a transition never shortens or moves a clip. `startTrimDrag('l'|'r')` moves one handle 1:1 while pinning the opposite edge, so a half-second drag grows the block by half a second (not by double) and the untouched edge holds still. Editing targets `selectedTransitionOf`, which `EditorStore.set` clears on any `selectedClipId` assignment that does not set it; the block's own pointerdown calls `selectTransition` and stops propagation so the lane's `onPointerDown` cannot wipe the fresh selection. Why: the engine only blends forward from the cut (`transitionInSpan` = `[c.start, c.start+duration]`) because the pipeline decodes the outgoing clip past its end via `outgoingTail` but never the incoming clip before its start, so `bias` is a lane-only affordance and the dissolve itself - and preview/export parity - are untouched; the cap `|bias| ≤ duration/2` guarantees the chip still covers the cut.
- Timeline drags (`startClipDrag`, transition `startTrimDrag`) measure their delta in scrolled timeline seconds via `timeAtClientX` (which adds `scrollLeft`), and `openDrag` pans the lane whenever the pointer rides either border while the lane overflows. Why: a long clip must trim/move all the way past the visible width, and a cut grabbed at one scroll position has to stay under the cursor as the lane scrolls instead of snapping back to where the drag began.
- Effect and filter blocks trim as uniform `[start, start+duration]` windows (`isUniformBlock`): the left edge moves `start` holding the end fixed, the right edge moves the end, both with `in` pinned at 0. Why: they have no finite media source to scrub into, so the media path's `in >= 0` clamp froze their left edge and made them trimmable from only one side.
- Speed ramps are piecewise-linear curves over normalized clip time; `clipDuration`/`sourceTime`/`speedAt` and the audio mix's playbackRate automation all derive from the same curve. Why: preview, export video and export audio stay in sync.
- Audio gain (volume, fades, ducking) comes from one `clipGainAt` function used by preview and export. Why: what you hear while editing matches the export.
- AI portrait effects use on-device MediaPipe segmentation loaded lazily (`ai.ts`); export awaits the model first. Why: no server video processing.
- Headless test Chromium can't decode H.264; use VP9/WebM files for automated checks.
- The categorized AssetBrowser draws preset thumbnails through the shared clip renderer and applies engine catalog IDs; unavailable licensed packs are explicitly marked. Why: galleries must represent actual output rather than decorative previews.
- Crop stores a normalized source rectangle; freeze clips store a source timestamp used by sourceTime. Why: preview and browser export share the same edit semantics.
- Illustrated stickers are vector shape clips drawn by stickers.ts; additions float onto a text lane above the row they were dropped on and seek past entrance animation. Why: artwork stays editable, is immediately visible above video, and never shares a line with the clip it decorates.
- Sticker/shape motion is one catalog in stickers.ts (`applyStickerMotion`) resolved from `shape.motion` (style/speed/intensity), applied by both `drawSticker` and `drawShape` on clip-local time; "auto" falls back to the artwork's own profile so nothing is ever still. Why: preview, gallery thumbnails and export animate identically from the same function.
- The preview loop's dirty-frame decision is `previewPaintAction` (perf.ts), driven by what the canvas is *actually showing*: its (timeline, time) key, whether that paint had every source decoded, and a revision bumped whenever `syncMedia` repositions a media element. It never re-renders faster than the project fps, and a source that was just repositioned is distrusted until its `seeked` event lands (or `SEEK_HOLD_MS` expires). Why: redrawing the whole composite at display refresh rate starved the video and the UI, but `renderFrame` fills the stage black wherever a source has no picture, and pausing both resizes the canvas (emptying it) and snap-seeks the video - so the one frame drawn on that pause edge was painted mid-seek, and the old "are the sources ready now?" check then went idle and froze the player on that black screen. A paint with a missing source is now unfinished, so it is repeated once the frame arrives; a stopped frame briefly holds the last good picture instead of flashing black, bounded by `PAINT_SETTLE_MS` so a dead signed URL can neither hang nor hammer the loop. Because a resize wipes the bitmap, the loop also keeps a snapshot (`freezeRef`) of the last wholly-painted frame and `previewPaintAction` returns "hold" to put it back up whenever the stage is empty and the real frame is still decoding - and a `renderFrame` that throws restores it too instead of freezing on a half-drawn stage.
- `sourcesReady` judges a frame by the clip kinds that actually need a decode (video/image, including a transition's `outgoingTail` frame) and requires `readyState >= 2`, a `src`, `!seeking` and a nonzero intrinsic width. Why: it is the loop's only knowledge of what `renderFrame` can paint, so a source it lets through half-loaded is what puts a missing layer on a black stage.
- A stopped playhead always sits on `lastFrameTime(timeline, fps)` (`duration - 1/fps`), and every seek, arrow step and skip lands on it through `clampPlayhead`. Why: clip spans are half-open, so the timeline's own duration is one frame past the last picture - the same frame export ends on (`0..ceil(dur*fps)-1`) - and running out of playback parked there, which painted a pure black stage instead of the scene that just ended.
- Gallery tiles share one rAF driver, one sample canvas and one layer canvas, redraw only while visible, back off while the timeline plays, and are memoized on catalog ids. Why: per-tile loops with per-frame canvas/Image allocation froze the preview whenever any clip was edited.
- Panels are memoized on their clip and subscribe to derived primitives (active cue id, clip-local time) instead of raw `store.time`. Why: the playhead ticks 60x a second and rebuilding the inspector or the caption list on each tick makes playback stutter.
- Gallery placement uses placement.ts to resolve selected or active visual media and seek within it. Why: quick-add works without selection and when the playhead is outside the selected clip.
- Caption timing edits pass through caption-edit.ts validation, and every cue also shows on the timeline as a block on its own caption line (`CaptionLane`): drag the body to move the phrase, drag either end to retime it, click to seek and open it in the caption editor. Why: retiming cannot silently make a cue inactive or non-finite, and cues drawn inside the video row looked like clips they were not - the cue list still lives in `caption_tracks`, so the lane and the panel are two views of one object.
- A timed caption can be converted into a normal text clip and removed from its cue track. Why: free transforms and keyframes reuse the editable overlay engine rather than duplicate it.
- Browser export uses a resolution-scaled numeric video bitrate with a quality floor. Why: small fallback-codec exports must retain text and artwork detail.
- `key.ts` keys only the isolated clip layer before color effects; tolerance/softness/spill are normalized 0–1.
- `mask.ts` uses normalized frame geometry and clip-local interpolated mask keyframes; feathering precedes destination-in compositing.
- `reframe.ts` tracks downsampled edge/motion saliency causally; cropRect always clamps the aspect-preserving crop inside the source frame.
- Generated photographic grades use filter-gen.ts, vector sticker families use sticker-gen.ts, and fonts share fonts.ts. Why: deterministic engine catalogs keep editor output and thumbnails consistent.
- Visual fades are independent from audio fades; clip-controls.ts provides envelopes, and clipGainAt applies clip-only mute. Why: preview and export must agree without changing unrelated clips.
- AudioClipVolume updates only its clip through EditorStore gestures. Why: dragging gain must not move clips or alter a track.
- Camera-movement effects derive their ramp from `effectProgress(t, blockDuration)`, threaded through `processLayer`/`applyGlobalFx`; the preview loop also syncs media on a `playing` edge, not only on a time change. Why: a stopped frame must be silent, and a 3s ramp must finish where the block ends in preview and export.
- The transition catalog lists only presets with distinct compositor math; legacy `vector-*` directional ids stay renderable but are never offered as presets. Why: directional look-alikes made the library read as fake variety.
- Placement is decided by the clip's own kind, never by the lane type: `activeEffectClips`/`gradeBlocksInLane`/`renderFrame`/`export` select work by `c.kind`, `isVisualClip(c)` decides what draws a layer, and `prevAdjacent`/`nextAdjacent` ignore clips that draw none - so a block an older project left inside a media lane still renders. What changed is where new blocks may *land*: `accepts` gives each kind exactly one lane type (`effect`→Effects, `filter`→Filters, media→Video, audio→Audio, text/shape→Text), and `addClipToTimeline` puts a block that has no free lane of its kind on a new lane spliced directly above the row it was dropped on, reusing the nearest lane of its kind at or above that row on later drops (or any existing lane of that kind when the addition aims at no row, i.e. a gallery click). Why: overlays stacked on the video row were unreadable and ungrabbable, while lanes still map 1:1 to the layer stack the compositor walks bottom-to-top.
- A filter is a trimmable `filterClip` block on a Filters lane, graded by `gradeFrame` inside the lane loop of `renderFrame` (not as a clip property), so it recolours the picture built at and below its own line and leaves overlays above it untouched. Why: export calls the same `renderFrame`, so a grade block previews exactly as it renders out; per-clip `clip.filter` grades keep working with no migration.
- Library tiles and the timeline drop share one placer (`applyPresetAt` in `library-drag.ts`, payloads tagged `preset:<tab>:<id>`). Why: clicking "+" and dragging to an arbitrary moment/lane can never drift into two different placement rules.
- Preview size is governed by `perf.ts` (`PREVIEW_LEVELS`, `observePerfFrame`): the loop measures each `renderFrame`, and because frame cost is essentially the pixel count it solves for the level that meets `1000/fps` instead of crawling down one rung at a time. Paused/scrubbed frames always render at `FULL_QUALITY`. Why: a heavy stacked scene (filters + adjustments + transition + effect blocks) needs ~230ms at 1280 on a modest machine, which starves rAF and makes both picture and voice stutter, while the same work at 400px is real-time; export is untouched because it calls `renderFrame` at project size.
- Playback rate is the user's clip speed: `resyncMedia` (with a per-clip `SyncGate`) NEVER modifies the rate - the element always plays at the nominal `speedAt(c, …)` value. Drift is corrected exclusively by seeking (repositioning), not by easing the rate, because pitch is not preserved and any automatic speed change is heard as the audio "getting faster." A clip that just entered the timeline is _placed_ by the caller via `SyncGate.positioned`, which is alignment, not correction. Why: the user explicitly requires that adding audio and hitting play must not alter the original speed; a prior rate-nudge path (±6%) was heard as speeding up.
- Pointwise color work reads/writes one `Uint8ClampedArray` (an `Int32Array` view measured slower) and takes every curve from a baked LUT plus a shared noise table, never per-pixel `Math.pow`/`Math.sin`/hashing. Why: on the target machine a bare byte loop costs ~8ms per 720p frame while three `pow` calls per pixel made a single filtered layer cost ~200ms.
- The clip color matrix runs through an SVG `feColorMatrix` (`color-interpolation-filters="sRGB"`) into a `blitCtx` canvas, verified once at runtime against `matrixInPlace` with a JS fallback. Why: `willReadFrequently` pins a canvas to the CPU and made the filtered blit 15.9ms instead of 1.1ms, and an ignored `ctx.filter` must never silently drop color work.
- The public landing page keeps every claim it makes in `site-data.ts` - including its own head/meta strings and the preset names the hero mock shows - and its hero illustration stays CSS-only (`EditorMock.tsx` + `.cutroom-*` rules in `styles.css`), while `landing.test.ts` asserts each quoted number against the real `FILTERS`/`EFFECTS`/`TRANSITIONS`/`ART_STICKERS` exports, proves the mock's names exist in those catalogs, and rejects any sentence that advertises a Pro-gated capability as if it worked. Why: importing an engine catalog into the route would bundle the canvas/WebCodecs engine into a marketing page, so the numbers are written out and a test is what keeps the copy honest - the page had promised a working auto-caption/transcription pipeline, "translation into 20 languages" and "nothing server-side" rendering that this build does not run. Every call-to-action targets `APP_PATH` (`/projects`) so the guard, not the page, decides between the app and `/auth`.
- Anything needing a model or service this app does not ship is locked in one place, `src/lib/pro-gate.ts`: `proLocked` decides, `PRO_COPY` holds the single "coming soon in the Pro version" notice together with the alternative that does work today, `ProChip` marks the control before it is clicked and `announcePro` raises the notice when it is. Effects are locked by catalog `group` through `isProPreset`, `applyPresetAt` is the one gate a locked preset must clear (the gallery "+" and a timeline drop both route through it), and the inspector's effect picker asks the same `isProEffect` so neither route can add one - while removing a locked effect an older project already carries is never blocked. Why: the five AI surfaces (auto-captions, caption translation, AI portrait effects, the avatar tab, the inspector picker) used to answer the same attempt five different ways - some hid the feature so it looked broken, one started a job that could not finish, and rendering a Pro effect into a gallery thumbnail would download the segmentation model for a preview nobody can use.
- Only AI features are ever gated: the four `ProFeature` surfaces and the `AI portrait` effect group. Every transition, filter and sticker and every non-AI effect is a free preset, and the gallery's `UNAVAILABLE` category set (`AssetBrowser.tsx`) may only name categories that ship no engine presets (licensed third-party packs, AI-only surfaces) - never a group the engine can render, which is why the `3D` transitions stayed available; `pro-gate.test.ts` asserts the sole effect lock is `AI portrait` and that no transition/filter/sticker is Pro.
- No competitor product name and no starter-template platform name appears in UI copy, landing copy, docs or code comments. Why: the app is presented as original work, so naming another product is both a trademark risk and an implicit claim of association, and a gallery notice plus one `fx.ts` comment had put such names back on screen; `landing.test.ts` walks `src/`, `public/`, `drizzle/`, `supabase/migrations` and the root docs/config files and rejects each banned name, which it builds from fragments so the guard file itself stays free of them.
- Copy takes exactly one timeline object and holds it on `EditorState.clipboard` (`clipboard.ts`): a clip of any kind, a transition on its own, or a caption cue aimed through `selectedCueId`. Why: a timeline object is not text and a media clip only means something inside the project that owns its asset, so the browser clipboard is never touched and the Paste button can name what it will place.
- A paste lands at the playhead on the lane `resolveNonOverlappingLane` picks (the same resolution `addClipToTimeline` uses), stepped past whatever already occupies that lane, and arrives without `transitionIn`. Content clips (video, image, audio) never overlap temporally on the same lane - when all existing lanes of that kind would cause overlap, a new lane is created. Overlay clips (effect, filter, text, shape) may share a lane even with temporal overlap because they composite as separate passes. Why: nothing the user already edited moves or overlaps to make room, and a blend belongs to a joint - reuse one by copying the transition itself, which clamps to `maxTransitionDuration` instead of refusing a tight seam.
- Only a left-click on empty lane clears selection (`data-track-id` handler bails on `e.button !== 0`): a right-click is opening the block menu and must not first wipe a Ctrl+A multi-selection. The context menu's `Combine` item re-runs `store.selectAllClips()` then opens the dialog. Why: right-click previously bubbled into the lane's `onPointerDown`, clearing every highlight the user had just made.
- Export is two stages in `ExportDialog`: `Combine` merges every lane into one MP4 (via `exportVideo`) and plays it back in a `<video>` preview; only then does `Export` download that already-rendered blob (`download` reuses `take.url`, no second encode). "Change settings" returns to the setup stage and revokes the object URL, and closing the dialog or unmounting revokes it too. Why: the user asked to see the combined full video before exporting, and re-rendering to save would double the encode.
- The timeline height is user-resizable through a `role="separator"` drag handle above it (`startTimelineResize` in the editor route): dragging up grows `timelineH` (clamped `200..innerHeight-240`) so more lanes fit, and the content row flexes to the remainder. Why: the fixed 300px lane forced horizontal scrolling and hid tracks the user needed to reach.
- The Audio library (`sfx.ts`/`AudioLibrary.tsx`) is a hybrid: synthesized cues (rendered by `renderSound`) and real recordings whose `Sound` carries a `url` under `/audio/...` (files in `public/audio/`). A `url` sound is fetched and decoded through one shared `AudioContext` for preview, and `+ Add` uploads the original file to the media bucket rather than re-encoding a WAV; `sfx.test.ts` renders only the synthesized set and asserts each real file exists on disk. Why: the user rejected synthesized instruments as fake, so genuine royalty-free recordings ship as static assets, kept separate from the procedural generator.
- The Audio panel's Record feature (`AudioRecorder.tsx` + `recorder.ts`) first asks the source - `microphone` (external) via `getUserMedia` with echo/noise/AGC off for clarity, or `browser` (tab/desktop audio) via `getDisplayMedia` keeping only the audio track - captures with `MediaRecorder` at 256 kbps, then decodes the blob to PCM and serializes a lossless WAV (`encodeWav`, now multi-channel interleaved) so duration is exact and export/transcription can range-read it. The take is uploaded through the same `uploadMedia` -> media bucket path, so `Save to library` persists it as a project sound and `Add to timeline` also places it. Why: browser `MediaRecorder` webm often reports no length and blob URLs fail range requests, so the recording is normalized to WAV and stored in Supabase like any other media; no server does the capture.
- The watermark (`watermark.ts` + `WatermarkPanel.tsx`) is a project-level `Watermark` on the `Timeline` JSON, not a clip, and `renderFrame` paints it as the final always-on-top pass so it is baked identically into preview and export. Its logo is an image `MediaAsset` referenced by `logoAssetId`; preview and export each resolve it to a decodable image (`getWatermarkImage` on `RenderOptions`) and the logo upload reuses the `uploadMedia` -> media bucket path. Why: an anti-copy mark must travel with the rendered file and cover the whole frame (single corner or a diagonal tiled field) at a chosen opacity, so it lives on the shared compositor rather than an editable lane. The live watermark is held on `EditorState.watermark` (NOT inside `timeline`), so no `{ tracks }` transform, drag, trim or undo/redo snapshot can drop it - the earlier design put it on the Timeline and edits kept wiping it. `setWatermark` changes it without touching timeline history, `renderFrame`/export read it from `RenderOptions.watermark` (a single source, never `timeline.watermark`), and the editor route folds it back into the persisted `projects.timeline` JSON on save so `loadEditor` hands it to the store constructor again. Removal flips `enabled` (never deletes the field), and it stays off only because the user turned it off - `watermark-persistence.test.ts` guards that edits, undo and reloads all keep it.
